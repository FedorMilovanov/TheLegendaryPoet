# Протокол агента: SUNO-клипы

## Назначение

Используй этот протокол для запросов на кадры, сцены, раскадровку, исправление
изображений и оживление клипа по песне SUNO. Для Lyrics и музыкального Style сначала
действуют правила `suno/AGENT.md`; этот документ не заменяет их.

## 1. Начало без лишних вопросов

Перед генерацией:

1. прочитай манифест проекта или профильный case;
2. установи последнюю корректировку пользователя — она важнее старого промта;
3. найди утверждённые референсы и уже выбранные кадры, проверив их наличие;
4. зафиксируй формат, стиль, continuity и что именно нельзя менять;
5. начни с короткого плана текущего раунда и сразу работай.

Не спрашивай то, что уже записано в репозитории. Не требуй полный бриф, если можно
начать с разумным вариантом. Вопрос допустим при реальной развилке, отсутствующем
обязательном исходнике либо перед внешней публикацией/правовым решением.

## 2. Баттлы без нарушения ограничений инструмента

Один **баттл** — один вызов генерации с вариантами, например `offer_options: true`,
показывающий пользователю двух кандидатов. Репозиторий не может отменять ограничения
конкретного инструмента.

- **Серия из трёх разных кадров:** три независимых баттла, по одному на каждый кадр.
  Независимые вызовы можно запускать параллельно.
- **Один кадр или одна точечная правка:** один вызов с вариантами. В текущем генераторе
  этот вызов уже даёт двух кандидатов; не запускай дубликаты, чтобы изобразить «3 баттла».
- Если пользователь просит три баттла одного и того же изображения, кратко объясни
  ограничение инструмента и предложи допустимый вариант. Новая отдельная просьба
  переделать кадр рассматривается как новая работа, а не как обход правила.
- Не выдавай один баттл за три и не называй три кандидата тремя завершёнными кадрами.
- Режим без вариантов допустим при прямой просьбе пользователя или когда так требует
  тип работы/инструмент.
- Ручной внешний видеосервис или другой генератор может иметь иной допустимый режим;
  ограничение текущего image tool не переносится на них автоматически.

Каждый вызов должен давать одно standalone-изображение на кандидата, не сетку, коллаж
или контрольный лист. Одинаковый промт может дать разный результат, но при системной
ошибке меняй одну главную переменную: референс, тип edit, выражение, масштаб или композицию.

## 3. Статусы результата

- **`no_selection` / `skipped`:** в интерфейсе нет выбора. Это не доказательство отказа.
  Инструмент мог не сохранить целевой файл; не утверждай, что он существует. Пользователь
  мог скачать кандидата напрямую и позже прислать его обратно.
- **`rejected`:** пользователь явно отклонил вариант или попросил его переделать.
- **`user_supplied`:** пользователь прислал изображение и попросил с ним работать. Его можно
  использовать по этому запросу без голосования, но общий канон оно не получает автоматически.
- **`accepted`:** конкретный кадр выбран или явно утверждён пользователем, а доступный файл
  найден. Только такой кадр становится каноном и основой оживления.
- **`aborted`:** выполнение прервано; это не завершённый баттл и не accepted.
- **`stopped`:** пользователь остановил работу. Любые автоматические повторы прекращаются.

Не запускай новый раунд только из-за `skipped`: следуй дальнейшей просьбе пользователя.
После явного `rejected` сделай короткую диагностику и допустимый инструментом повтор.
Команда «другие/дальше» отменяет старую очередь ремонтов; «хватит» останавливает всё.

## 4. Референсы и независимость кадра

Перед вызовом обозначь роль каждого изображения: композиционная основа, мастер личности,
отдельный костюм, мастер существа/реквизита, expression reference или accepted continuity.
Обычно хватает 1–3 референсов. Не добавляй изображение только «чтобы было».

Лицо, костюм и оружие — разные оси канона. Не бери лицо из нового costume reference,
если лицо уже задано identity master. Число и стороны оружия фиксируются проектом/шотом,
а не временем суток или присутствием монстра.

Для редактирования первым передавай кадр, который нужно сохранить. Для новой сцены не
называй её «pixel-perfect». Подробнее — [VISUALS.md](./VISUALS.md).

## 5. Порядок производства

1. Сначала зафиксируй план кадров и визуальный канон.
2. Генерируй статику в допустимом баттл-режиме.
3. Веди короткий статус: `pending / battling / no_selection / rejected / user_supplied /
   accepted / needs-redo / stopped`.
4. После раунда сообщай только фактические результаты и доступные пути.
5. Оживление начинай лишь для accepted-кадров и по [ANIMATION.md](./ANIMATION.md).
6. Для выдачи на скачивание используй `present_file`; не заставляй пользователя искать
   файл в глубокой рабочей вложенности.

## 6. Definition of done

Кадр завершён, когда:

- пользователь выбрал или явно утвердил его;
- файл реально существует в workspace;
- формат и отсутствие полос проверены для финального использования;
- личность, костюм, реквизит, существо и continuity соответствуют манифесту;
- нет незаявленных людей, текста, водяных знаков и дефектов анатомии;
- выбранный путь записан в проект.

Серия не считается завершённой по количеству вызовов: нужны принятые файлы по всем
запрошенным кадрам либо явное решение пользователя остановиться/пропустить.

Генерация, добавление в Git, публикация и музыкальный релиз — разные действия. Не
выдавай одно за другое и не заявляй о прослушивании/просмотре без фактической проверки.
