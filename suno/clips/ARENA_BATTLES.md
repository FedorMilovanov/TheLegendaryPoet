# Arena Agent: практический playbook изображений и баттлов

Короткие рабочие сценарии к [AGENT.md](AGENT.md) и [VISUALS.md](VISUALS.md). Здесь не
дублируются общий контракт 16:9 и все правила стиля; фиксируются решения, которые помогают
улучшать кадр через отбор, а не через бессмысленное число повторов.

## 1. Выбор количества баттлов

В текущем image tool один вызов с вариантами — **один Battle, два анонимных кандидата**.

| Запрос | Что делать в текущем image tool |
|---|---|
| Один новый кадр | Один вызов с вариантами |
| Одна локальная правка одного кадра | Один вызов с вариантами в текущем раунде |
| Три разных кадра/сцены | Три независимых вызова с вариантами; можно параллельно |
| Три разных кадра на основе одного base/reference | Три независимых вызова, но у каждого своя композиция и действие |
| Три баттла одной и той же правки | Не запускать три `offer_options`-вызова на один requested image/edit; проверить ручной UI или другой инструмент отдельно |
| Новый раунд того же кадра | По явной просьбе: stochastic retry с прежними условиями либо корректирующий повтор с новой гипотезой |

`no selection/skipped` не означает плохой кадр или запрет: файла нет, автоматически не
повторять. `awaiting_user_response` тоже не является принятием. Accepted — сохранённый файл
плюс явный выбор пользователя.

**Это ограничение конкретного инструмента, не Arena вообще.** В ручном интерфейсе или у
другого агента три отдельных баттла одного кадра с референсами могут быть допустимы. Тогда
можно подготовить три самостоятельных запуска/промта для этого интерфейса, но нельзя выдавать
их за выполненные без фактических результатов. Референсы сами по себе не запрещают и не
разрешают тройной режим: решают возможности конкретного UI/API.

## 2. Три независимые генерации с референсом

Один и тот же base можно использовать в трёх баттлах, если результаты действительно нужны
как **разные шоты**. Например: общий план локации, средний силуэт героя, заднебоковой кадр
с вороном. В каждом промте заново задать размер фигуры, ракурс, место в кадре, действие и
что сохранить/заменить.

Нельзя назвать разными шотами три одинаковых исправления букв, три одинаковых поворота лица
или три варианта одной композиции с косметически изменёнными словами. В текущем image tool
для них нужен один баттл в раунде; отдельный ручной режим проверяется по его собственным правилам.

Порядок обычных ролей:

1. FIRST base — текущая композиция/геометрия, которую надо сохранить.
2. SECOND identity/costume/prop master — конкретная сущность или материал.
3. THIRD — только необходимая дополнительная непрерывность.

Не смешивать несколько конфликтующих base-кадров ради страховки. Для костюма Легендарного
Поэта брать один подходящий ракурс из [его пакета](references/legendary-poet/README.md).

## 3. Два типа повторов

### Stochastic retry — те же условия

Модель и анонимные кандидаты могут дать другую реализацию при неизменных промте и референсах.
Если пользователь просит ещё попытку, **повтор с прежними условиями нормален**: иногда он
исправляет единичный неудачный draw без изменения канона. Записать честно: `same conditions,
new draw`. Это не новый метод и не гарантия улучшения.

### Corrective retry — новая гипотеза

Если один и тот же дефект повторяется системно, назвать его одной фразой: **лицо / буквы /
масштаб / позиция фона / материал / анатомия / действие**. Затем менять преимущественно одну
переменную:

- добавить или заменить точный reference;
- сократить промт и убрать второстепенные действия;
- перейти от recreate к localized edit либо наоборот;
- изменить композицию, если старая физически провоцирует ошибку;
- для текста добавить отдельный typography-reference;
- для рискованного лица выбрать спину/профиль/дистанцию, если это соответствует сцене;
- для motion разбить действие на наблюдаемые стадии.

Не заваливать следующий промт десятками «не». Повтор с теми же условиями проверяет дисперсию;
повтор с новой гипотезой проверяет метод. Оба допустимы по запросу, но бесконечные
автоматические повторы без выбора и диагностики — нет.

## 4. Текст и логотип: отдельный режим

Генератор не является надёжным текстовым рендерером. Для исправления надписи:

1. FIRST — понравившаяся сцена; SECOND — точный raster typography-reference, если он есть.
2. Просить localized text repair только в области надписи либо полностью перестроить надпись
   на той же сцене, но не перерисовывать весь пейзаж и персонажей.
3. Написание дать отдельной строкой. Не просить модель сочинить или «улучшить» текст.
4. После выбора проверить каждую букву визуально. Если буквы снова ломаются, менять метод
   (точный референс/локальная маска/типографика в редакторе), а не бесконечно повторять промт.

Промт «сохрани каждую букву» не является гарантией. Точное написание подтверждает просмотр
или отдельный типографический этап, не текст запроса.

## 5. Дальний фон, blur и пустые зоны

Для далёких фигур задавать четыре независимых параметра:

- **физическое место:** где именно стоят относительно моста, скалы, холма;
- **видимый масштаб:** маленькие силуэты, сколько примерно высоты кадра занимают;
- **резкость:** сильный optical/atmospheric background blur, без читаемого лица;
- **запретную зону:** какой главный объект должен остаться пустым/незанятым.

«Очень далеко» без места и масштаба часто превращается в крупную резкую фигуру на переднем
объекте. Если это повторяется, менять композицию/точку съёмки, а не только усиливать отрицания.
Не обещать, что blur сохранит лицо: нужна ещё дистанция, угол и маленькая видимая величина.

## 6. От still к motion и выдаче

- Видео-промт начинается с **уже выбранного** still. Сначала принадлежности кадра, затем
  действие по стадиям, затем камера и условие сохранения анатомии/географии.
- Круговой облёт, исчезновение, прыжок и реакция фона не смешивать в один неуправляемый трюк;
  см. [ANIMATION.md](ANIMATION.md).
- После явного выбора проверить реальный файл, при необходимости размеры, открыть его через
  `present_file` и записать путь. Не называть открытый чатом кандидат сохранённым мастером.
- Если Battle остался без выбора, пользователь может сам скачать кандидата и прислать его как
  base/reference. Такой файл получает статус `user_supplied`, а не ретроактивный `accepted`.

## 7. Минимальная запись без мусора

Для проекта достаточно: shot, тип раунда (`same conditions / new hypothesis`), результат и
выбранный путь. Не копировать в репозиторий переписку, все отклонённые кандидаты, внешние логи
или неиспользуемые серии. Канонизировать только небольшие повторно полезные мастера; остальное
остаётся рабочим медиа.
